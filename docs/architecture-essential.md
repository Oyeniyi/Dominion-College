# Architecture Essentials

**Status:** Required review rules for the target system; no application implementation exists yet.  
**Last reviewed:** 2026-10-27  
**Authority:** Mandatory rules below derive from the draft [`../prd.md`](../prd.md), [`architecture.md`](./architecture.md), and [`../AGENTS.md`](../AGENTS.md). Proposed ADRs are not accepted decisions. [`security-specification.md`](./security-specification.md) exists as a proposed reference only, pending formal approval; it is not the governing security baseline. No source code, product dependency manifests, or automated architecture checks are present. Do not claim a rule is enforced until an implementation and verification exist.

Use this document during design and code review. A **Mandatory** rule requires correction or explicit architectural approval to violate. An **Advisory** rule may be departed from with a documented reason. Any proposed exception affecting security, privacy, student media, or scope requires the appropriate school/project-owner approval; document approved material deviations in `architecture.md` and an ADR.

| **AE-01 — Dependency direction** | Dependencies flow inward: presentation and transport call application services; services depend on domain rules and explicit data/storage interfaces; infrastructure implements those interfaces. Domain rules must not depend on UI, framework routes, provider SDKs, or infrastructure. Do not introduce cyclic module dependencies. | Keeps business rules testable and prevents framework/vendor concerns from controlling domain behavior. | Public UI, admin UI, request boundary, application services, domain rules, data/storage adapters. | A route validates a request, calls `CreateEnquiry`, and the service uses a repository interface implemented by the database adapter. | A database adapter imports a page component or a domain service imports a framework router; service A and service B import each other. | **Automatable candidate:** dependency graph/linter rules for allowed import directions and cycle detection in CI. **Manual:** review module boundaries. No such check exists yet. | Architecture §§5, 7; PRD §9.3, NFR-07; ADR-001 (Proposed). | Mandatory |
| **AE-02 — Component ownership and separation** | Public rendering, protected administration, request validation, authorization, business rules, persistence, media handling, and error mapping have distinct responsibilities. UI components do not own privileged business rules or database credentials. | Prevents duplicated logic and frontend-only security; makes failure behavior consistent. | Public presentation, admin interface, request boundary, authorization, application services, query/data adapters, media workflow. | Both an admin form and a server action call the same validated content service; public reads use a public-safe query. | A page component directly mutates a database using a privileged key, or authorization exists only in hidden buttons. | **Automatable candidate:** static checks for forbidden imports/client exposure; tests for shared service behavior and direct unauthorized requests. **Manual:** responsibility review. Not implemented. | Architecture §§5, 8; FR-09; NFR-04, NFR-07; ADR-001/003 (Proposed). | Mandatory |
| **AE-03 — Data ownership and publication boundary** | The application owns its content, site settings, publication status, and enquiry records. Public queries may return only approved and published content. Draft, unpublished, unapproved, or private data must remain unavailable through public routes and guessed IDs/URLs. | Publication status is a security and privacy boundary, particularly for private enquiries and images of minors. | Content services, public read layer, admin read layer, database, media storage, cache/CDN. | A public article query filters to published records and returns only public fields; private enquiries are queried only after server authorization. | Filtering drafts only in the browser, returning all fields from a public API, or exposing an unpublished object at a predictable public URL. | **Automatable candidate:** integration/E2E tests for draft and private-data access by anonymous users; schema/query tests; cache header checks. **Manual:** publication and media review. Not implemented. | Architecture §§2, 5–6, 8; FR-06–FR-09; NFR-05, NFR-08; ADR-002/004 (Proposed). | Mandatory |
| **AE-04 — Authentication and authorization boundary** | Authentication establishes identity; it does not grant permission. Every protected read, mutation, and media operation enforces server-side authorization and active-account policy. Unknown/invalid identity or permission fails closed. | Direct requests must not bypass UI restrictions; enquiries and admin functions are sensitive. | Request boundary, identity/session adapter, authorization policy, admin queries, mutations, private media. | A server operation verifies session, active status, and permission for the specific action before loading or changing a record. | Dashboard links are hidden for non-admins, but the backend endpoint accepts their request; missing identity-service response defaults to admin. | **Automatable candidate:** integration/E2E authorization matrix for anonymous, inactive, and unauthorized actors; static checks for protected handlers missing policy wrapper. **Manual:** account lifecycle and role review. No policy/check exists yet. | Architecture §§5, 8; FR-09; NFR-04, §14.2; ADR-003 (Proposed). | Mandatory |
| **AE-05 — API and request contract** | Treat every client request as untrusted. Validate and normalize input at the server boundary; return documented, safe outcomes for validation, authorization, not-found, conflict, and dependency failures. Never expose stack traces, credentials, or private records. Do not claim success until the corresponding persistent operation succeeds. | Ensures predictable clients, protects data integrity, and prevents false success or information disclosure. | Public enquiry endpoint, admin operations, upload interface, error mapping, UI forms. | Invalid form fields return field-level errors; an enquiry response indicates success only after commit. | Client-only validation, accepting arbitrary object fields, or returning success before the database confirms persistence. | **Automatable candidate:** contract/schema tests, negative-input tests, response-shape tests, E2E persistence assertions, secret-leak checks. **Manual:** review error text and privacy. Not implemented. | Architecture §§5–6, 10; FR-04, FR-06–FR-09; NFR-04; ADR-001/003 (Proposed). | Mandatory |
| **AE-06 — Database access and migrations** | Only trusted server-side data-access code may use privileged database credentials. Access must be least-privilege, parameterized/ORM-safe, and server-validated. Schema changes use reviewed migrations with integrity constraints; no production data changes by unreviewed ad hoc scripts. | Protects private records and integrity and supports controlled recovery/evolution. | Application services, repositories/data adapters, database, migration/release process. | A server-side repository performs parameterized queries with a restricted application credential; schema updates are versioned migrations. | Browser code contains a database URL/service key, a query concatenates user input into SQL, or production schema is changed manually without a recorded migration. | **Automatable candidate:** secret scanning, dependency/static SQL checks, migration CI against a disposable database, schema drift check. **Manual:** privilege and migration review. No DB or CI exists. | Architecture §§6, 8–9; PRD §8.3, §9.2–9.3, NFR-04, NFR-07; ADR-002 (Proposed). | Mandatory |
| **AE-07 — Secret and environment configuration** | Secrets and environment-specific credentials are supplied through protected runtime configuration, never committed, logged, exposed to the browser, or placed in editable public site settings. Required configuration must be validated; missing critical values fail explicitly rather than using guessed defaults. | Prevents credential disclosure and unsafe behavior across environments. | Build/deploy configuration, application runtime, identity/database/storage adapters, site settings. | A server-only database secret is injected by the deployment secret manager; a missing WhatsApp number disables the contact link with an explicit safe state. | A real token is committed, serialized into client props, stored in CMS settings, or replaced with a guessed production number. | **Automatable candidate:** secret scanners, client-bundle string scan, config-schema test, CI check against real `.env` files. **Manual:** provider access review. No automation exists. | Architecture §§6, 8–9; PRD §9.3, NFR-04, NFR-07; ADR-001–004 (Proposed). | Mandatory |
| **AE-08 — Error handling and failure semantics** | Failures must be explicit, safe, and truthful. Do not swallow exceptions, produce success-shaped fallbacks, expose internal errors, or retry non-idempotent writes blindly. Public pages may degrade independently of private admin services only where no private data is involved. | Prevents silent data loss, duplicate writes, leaked internals, and false user confidence. | Request boundary, application services, persistence, identity, media, UI, operations. | Database failure returns a safe failure state and does not report enquiry submission success; a public static page remains available if identity is down. | Catch-all returns an empty success response; a failed write is retried without duplicate semantics; raw stack trace is shown to visitor. | **Automatable candidate:** fault-injection tests for DB/storage/identity errors, retry/idempotency tests, response assertions, static analysis for empty catches. **Manual:** recovery/runbook review. No checks exist. | Architecture §§5, 7, 10; FR-04, FR-09; NFR-04, NFR-06; ADR-002–004 (Proposed). | Mandatory |
| **AE-09 — Transaction and cross-service consistency** | Changes that must be all-or-nothing within the database use a transaction. Do not assume a transaction spans database and object storage. Media must not become publicly reachable until storage, metadata, approval, and publication state are consistent. An enquiry is acknowledged only after persistence. | Avoids partial published content and enquiries that are not actually stored. | Enquiry/content services, database, media workflow, publication/read layer. | Upload privately, validate, persist metadata/status, then publish an approved rendition; on failure leave it unpublished and report the failure. | Mark an image public before upload finishes, or show enquiry success before its database commit. | **Automatable candidate:** integration tests with storage/DB failure injection; transaction tests; assert no public reference after partial failure. **Manual:** orphan cleanup and recovery procedure review. Not implemented. | Architecture §§6–7, 10; FR-04, FR-06–FR-07; NFR-06; ADR-002/004 (Proposed). | Mandatory |
| **AE-10 — Logging and sensitive data** | Logs and telemetry contain only the minimum operational details needed. Never log passwords, tokens, credentials, full enquiry contents/contact fields, private media URLs, or student-identifying metadata unless a separately approved policy requires and protects it. | Logs often have broader access/retention than application records; sensitive data must not leak indirectly. | Request boundary, error handling, database/media adapters, monitoring/logging. | Log a safe error category, timestamp, and non-sensitive correlation ID. | Log the full failed form payload or include auth headers in exception output. | **Automatable candidate:** logger tests with sensitive sentinel values, static scanning for request-body logging, redaction tests. **Manual:** log access/retention review. No log stack exists. | Architecture §§6, 8; NFR-04–NFR-05; PRD §12; ADR-003/004 (Proposed). | Mandatory |
| **AE-11 — AI tool permissions and data** | No runtime AI/model/orchestration is in MVP. Do not send sensitive student or enquiry information to third-party AI services. AI-assisted development must follow approved data classifications and access policy; absent approval, use only public/non-sensitive project information. | Avoids introducing unauthorized AI processing or disclosing personal data. | Development tools, source/data fixtures, runtime integrations, external API boundary. | Use synthetic enquiry fixtures in an approved coding tool; no AI endpoint or model is deployed for visitors. | Upload real enquiry exports, identifiable student photos, or sensitive school records to an unapproved model/service; add an AI admissions chatbot without scope approval. | **Automatable candidate:** dependency/API allowlist, CI scan for known AI SDKs/endpoints, fixture checks. **Manual:** tool/data approval and outbound traffic review. No enforcement exists. | Architecture §§2, 3, 6, 8; PRD §2.2, NFR-05; ADRs none (runtime AI excluded). | Mandatory |
| **AE-12 — No circular dependencies** | Modules and services must form a directed acyclic dependency graph. Cross-component collaboration uses inward-facing interfaces or application orchestration, not mutual imports or callbacks that create cycles. | Cycles obscure ownership, complicate initialization/testing, and make changes ripple unpredictably. | All application modules and shared libraries. | `EnquiryService` depends on `EnquiryRepository` interface; the infrastructure adapter implements it. | `EnquiryService` imports `NotificationService`, which imports `EnquiryService` to call back into it. | **Automatable candidate:** dependency-cruiser, Madge, language/project graph checks in CI, if compatible with selected stack. **Manual:** review ownership boundaries. No tool configured. | Architecture §5; PRD §9.3, NFR-07; ADR-001 (Proposed). | Mandatory |
| **AE-13 — External integration boundary** | Only approved integrations may receive data. WhatsApp is a user-initiated click-to-chat link, not proof of delivery. Analytics, maps, email/SMS, advertising, automated WhatsApp, and other APIs require business, privacy, and security approval plus documented data/failure contracts. | Limits vendor exposure and unreviewed processing of personal information. | Public contact UI, application services, external API adapters, privacy/configuration. | Render a configured WhatsApp link and retain the website enquiry form as an alternative. | Send enquiry data to an analytics/marketing service or claim a WhatsApp message was delivered without an approved API and evidence. | **Automatable candidate:** outbound dependency/domain allowlist and integration contract tests. **Manual:** privacy/security review and provider approval. No integration enforcement exists. | Architecture §§2, 4, 6; FR-05, FR-08, NFR-05; ADR-004 (Proposed). | Mandatory |
| **AE-14 — Caching and private data** | Only public, approved content may be cached publicly. Admin sessions, private enquiries, drafts, and unpublished assets must not enter shared caches. Publication/unpublication cache behavior must meet an owner-approved freshness target; until then, prefer correctness over stale visibility. | Prevents private-data leaks and stale exposure after content is unpublished. | Public query layer, admin routes, framework cache, CDN, media storage. | Public article listing uses explicitly published records; dashboard responses are private/no-store or equivalently isolated. | Shared cache keys omit user/authorization context or cache a dashboard response for public reuse. | **Automatable candidate:** response cache-header tests, cross-user cache-isolation E2E tests, publication invalidation tests. **Manual:** CDN/provider configuration review. No implementation exists. | Architecture §§4, 7, 10; FR-06, FR-09–FR-10; NFR-08; ADR-001/004 (Proposed). | Mandatory |
| **AE-15 — Data ownership and schema authority** | Each persistent entity has one authoritative owner/service. Other components access it through its defined interface; no second store may silently become the source of truth. Final schema, retention, deletion, and migration policy must be approved before production data is collected. | Prevents divergent records and unsafe handling of personal data. | Application services, database, media storage, integrations, migrations. | Enquiries are authoritative in the application database; media bytes are in storage and database holds their metadata/reference. | Copy enquiries into an unapproved spreadsheet/analytics system and let both stores be edited independently. | **Automatable candidate:** schema/migration checks and data-flow inventory in CI/review. **Manual:** ownership, retention, and export review. No schema/store exists. | Architecture §§6, 9; PRD §8.2–8.3, NFR-05–NFR-07; ADR-002/004 (Proposed). | Mandatory |
| **AE-16 — Dependency and framework selection** | Keep dependencies minimal and maintained. Do not treat proposed ADR technology as accepted; adding a framework, provider SDK, queue, AI client, or external service requires accepted ADR/explicit approval and current compatibility/security review. | Avoids unapproved commitments and unnecessary supply-chain/operational risk. | Build system, application modules, runtime, deployment. | Add a provider SDK only after the provider and data flow are approved and ADR is accepted. | Install the proposed ORM or cloud SDK solely because it appears in the research document. | **Automatable candidate:** lockfile audit, license/vulnerability scanning, dependency allowlist and policy checks. **Manual:** ADR and vendor review. No manifest or CI exists. | Architecture §11; PRD §9.1, §9.3; ADR-001–004 (all Proposed). | Mandatory |
| **AE-17 — Observability and recovery** | Production errors must be diagnosable without sensitive payloads; backups and restoration must be operationally documented and restoration tested before relying on them. Monitoring, retention, alerts, and recovery targets require named ownership and approval. | A backup is not a recovery capability until restoration is demonstrated; unowned alerts do not ensure response. | Runtime, database, storage, deployment, logging/monitoring, operations. | A restore exercise validates data in an approved environment and records evidence without exposing real enquiry data unnecessarily. | Claim backups are sufficient without restore tests, or route alerts to an unowned destination. | **Automatable candidate:** backup job status/restore smoke checks and alert-routing checks in operations pipeline. **Manual:** restore drill, incident exercise, owner approval. No operational systems exist. | Architecture §§9–10; NFR-04, NFR-06; PRD §15, §17–18; ADR-002/004 (Proposed). | Mandatory |
| **AE-18 — Shared domain logic** | Validation, publication rules, status transitions, and permission checks must have one authoritative implementation per business rule and be reused across entry points. Client-side checks may improve UX but cannot replace server-side enforcement. | Prevents inconsistent behavior between pages, forms, admin actions, and APIs. | Public/admin UI, request boundary, services, repositories. | Server service validates article status before publish; UI invokes it and displays returned field errors. | Different endpoints implement different rules, or a button disables invalid input while the API accepts it. | **Automatable candidate:** unit tests for shared rule functions plus integration tests across each endpoint; duplication/static checks where practical. **Manual:** code review. No code/tests exist. | Architecture §§5–6; FR-04, FR-06–FR-09; NFR-04, NFR-07; ADR-001/003 (Proposed). | Mandatory |
| **AE-19 — Advisory: framework portability** | Prefer framework-neutral domain/service code and isolate provider-specific APIs behind adapters, unless using a provider feature materially simplifies the approved design. Document any deliberate coupling and exit/data-export path. | Reduces migration friction while avoiding premature abstraction. | Application services, database/storage/identity adapters, deployment. | A storage interface hides provider-specific upload calls from publication rules. | Domain rules rely throughout on a single vendor SDK without documented rationale. | **Automatable candidate:** import boundary rules; **manual:** architecture review and export test plan. | Architecture §§5, 9, 12; G6; ADR-001–004 (Proposed). | Advisory |
| **AE-20 — Advisory: async and event infrastructure** | Do not introduce queues, event buses, workers, or scheduled jobs until an approved requirement needs asynchronous delivery or processing. If introduced, define ownership, retry, idempotency, privacy-minimized payload, observability, and failure handling first. | Current MVP is satisfiable through synchronous requests; extra infrastructure adds operational cost and failure modes. | Application services, notification/media workflows, infrastructure. | Persist enquiry synchronously and omit a queue until notifications are approved. | Add a queue for hypothetical future messaging with no user story, owner, or retry contract. | **Automatable candidate:** dependency review/allowlist; **manual:** ADR and requirement trace. | Architecture §7; PRD §6.3, §16; ADR-002/004 (Proposed). | Advisory |

## Automation Candidates (Not Yet Enforced)

The following checks could be implemented after the stack and source tree are approved. None exists in the current repository:

- Dependency direction and cycle detection (AE-01, AE-12, AE-19).
- Secret scanning, dependency vulnerability/license review, and client-bundle checks (AE-06, AE-07, AE-16).
- Authorization and public/private publication integration tests, including cache isolation (AE-03, AE-04, AE-14).
- Request contract, validation, transaction, retry, and fault-injection tests (AE-05, AE-08, AE-09, AE-18).
- Sensitive-data logging/redaction tests (AE-10).
- Outbound integration allowlist and detection for unapproved AI/provider SDKs (AE-11, AE-13).
- Migration checks, backup verification, and restore smoke tests (AE-06, AE-15, AE-17).

Code review must still verify privacy approvals, access policy, public content/media authorization, exception decisions, and operational ownership; tooling cannot establish those approvals.

## Review Checklist

For each change, reviewers should ask:

1. Does the dependency direction remain acyclic and within module responsibilities?
2. Are public, draft, unpublished, and private records separated server-side?
3. Are identity, authorization, data validation, and secrets handled at trusted boundaries?
4. Are errors truthful and safe, and are writes transactionally/idempotently correct?
5. Could logs, caches, integrations, or AI tools expose sensitive information?
6. Are external services and dependencies approved and documented?
7. Are required automated checks present and passing, and are remaining manual decisions recorded?
8. Does a deviation require an ADR or explicit school approval?

## Known Limitations

This ruleset describes target constraints, not current enforcement. The application, CI, security specification, dependency policy, role matrix, final API contracts, data schema, and deployment environment do not yet exist. Requirements with unresolved business policy must not be interpreted as permission to invent one.
