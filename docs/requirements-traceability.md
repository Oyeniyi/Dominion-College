## 1. Status definitions

Statuses are recorded separately for design, implementation, and verification to avoid conflating planning with delivery.

| Status | Meaning |
|---|---|
| **Not Analyzed** | No adequate analysis or trace has been recorded. |
| **Designed** | A design or specification addresses the requirement; it may still be proposed/unapproved. See the evidence column for approval state. |
| **Planned** | One or more backlog tasks propose implementation or verification; no implementation is implied. |
| **Implemented** | The behavior/control exists in the product and has been reviewed. A task or specification alone is insufficient. |
| **Verified** | Relevant verification ran against the implemented change and has recorded passing evidence. A plan or test definition is insufficient. |
| **Blocked** | Work cannot safely proceed until the named decision, input, or prerequisite is resolved. |
| **Deferred** | Explicitly postponed with an approved disposition, owner, and scope/version. |
| **Rejected with Approval** | A requirement or proposed capability has been formally rejected by its authorized owner. |

For table readability:

- **D** means design status; **I** means implementation status; **V** means verification status.
- **D: Designed (proposed)** means a document describes a candidate solution but it is not necessarily approved.
- **I: Not started** and **V: Not run** reflect the repository baseline, not a judgment about future feasibility.
- **Blocked** identifies a known unresolved dependency. It does not mean the requirement itself is rejected or deferred.
- A verification alias in a row points to §2's proposed verification method. Results remain **Not run** until actual evidence is recorded.

## 9. Coverage-gap and consistency register

### 9.1 Requirements without adequate design coverage

The design documents cover the broad planned experience, but design coverage is not equivalent to a complete or approved contract. Known gaps:

1. **API/schema decisions remain incomplete:** About/Academics edit operations, privacy-acknowledgement evidence, field/size limits, entry-level values, state transitions, pagination, media serving, cache freshness/invalidation, retry/idempotency, and deletion/retention need resolution. Related requirements: FR-02/03/04/06/07/09; NFR-01/04–08; SEC-05/06/08/09/12/16/20; AE-05/09/14/15.
2. **Identity and authorization design is not approved:** account owner/lifecycle, roles/action matrix, MFA/recovery, session expiry, image approval authority, and who may export/delete/change settings are unresolved. Related requirements: FR-09; NFR-04/05; SEC-01–05/16/18; AE-04.
3. **Privacy/child-protection governance is incomplete:** jurisdiction/legal review, purpose/notice, acknowledgement, retention/deletion, access/correction/export, media authorization evidence, withdrawal/takedown, and backup expiry need authorized decisions. Related requirements: FR-04/07; NFR-05/06; SEC-08/09/12/16/17/20.
4. **Operations and measurable service targets are incomplete:** workload, performance targets, RTO/RPO, provider/data location, monitoring/incident ownership, rate limits and recovery capacity are not established. Related requirements: NFR-01/04/06; SEC-10/15/17/18/21; AE-13/17.
5. **School content and visual approvals are incomplete:** official copy/contact details, entry levels, academics, logo usage, photographs and permissions require school validation. Related requirements: G1–G5; FR-01–08/10; NFR-02/03/05.
6. **AI has no runtime feature or evaluation strategy:** runtime AI is explicitly outside MVP. Do not invent AI behavior, tests, or evaluation thresholds; reopen only after approved scope, privacy/security review, and evaluation specification.

### 9.2 Requirements without implementation tasks or with incomplete task trace

- The backlog contains tasks for all core PRD goals, FR-01–10, and NFR-01–08, but it does not prove implementation. TASK-001 is Done as a documentation-reconciliation task; the other tasks remain unstarted/blocked. No application requirement is thereby marked Implemented or Verified.
- `TASK-031` covers `SEC-01–SEC-20` and selected AE controls, but omits **SEC-21** (secure deployment/configuration) and **SEC-22** (security testing/change control). Related deployment/runbook tasks exist, but update TASK-031's explicit requirement trace or add appropriately scoped work when the backlog is next maintained.
- No dedicated task exists for optional analytics from PRD §13. It is not approved baseline scope; if selected, add a privacy-reviewed, acceptance-defined task before implementation.
- No dedicated runtime AI feature/evaluation task exists; this is correct for the current MVP exclusion. Any future AI scope requires an approved spec and new traceable tasks.
- Cross-cutting governance tasks (for example TASK-001/002/008/009) cite product/architecture needs rather than an individual user-facing FR. Their engineering justification is specification consistency, approved technical decisions, reproducible builds, and quality/security controls (G6, NFR-04/07, AE-01/05/07/12/15/16). No task is identified as wholly orphaned, but several tasks depend on proposed `AE-*`/`SEC-*` identifiers which themselves need authority reconciliation.

### 9.3 Verification coverage gaps

- **No actual tests or test IDs exist yet.** The `V-*` catalog is a proposed mapping to test levels in `testing-strategy.md`; all outcomes are Not run.
- **No CI or test runner exists.** Product test coverage cannot be inferred from agent-skill tests in `.agents/skills/`.
- The testing strategy covers unit, component, integration, API contract, DB, E2E, responsive, accessibility, security, performance, reliability, migration, and AI applicability, but it does not enumerate executable test cases. Each implementation task should add case-level IDs/names and reports when tooling is approved.

- PRD analytics metrics have no accepted measurement design or verification; optional status must remain explicit.
- No runtime AI tests are applicable now. A future AI feature is untestable for acceptance until its evaluation criteria, test corpus/data protections, model/versioning and approval process are specified.
